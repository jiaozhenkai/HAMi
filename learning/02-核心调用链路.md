# 核心调用链路

本文档用**时序图**详细描绘 HAMi 的几条核心调用链路。每条链路都标注了关键源码位置（`文件:行号`），方便对照阅读。

## 四、Bind 链路（阶段 3 详解）

**入口**：`pkg/scheduler/routes/route.go:114` → `Bind()` → `pkg/scheduler/scheduler.go:1025`

```mermaid
sequenceDiagram
    autonumber
    participant KSC as "kube-scheduler"
    participant B as "Scheduler.Bind()"
    participant DM as "device.GetDevices()"
    participant NL as "nodelock"
    participant API as "kube-apiserver"

    KSC->>B: POST /bind (ExtenderBindingArgs:<br/>PodName, PodNamespace, PodUID, Node)

    B->>B: 从 lister 获取 Pod
    alt Pod 不存在
        B->>B: 清理残留分配
        B-->>KSC: 返回错误
    end

    B->>B: 获取目标节点
    alt 节点不存在
        B->>DM: releaseAllDevices() 释放所有锁
        B-->>KSC: 返回错误
    end

    B->>API: patch Pod: bind-phase=allocating, bind-time

    rect rgb(208, 2, 27, 0.1)
        Note over B,NL: acquireNodeLocks() 获取分布式锁
        loop 每个设备后端 (按 key 排序, 确定顺序)
            B->>DM: LockNode(node, pod)
            DM->>NL: nodelock.LockNode()
            NL->>API: 读取节点 hami.io/mutex.lock 注解
            alt 无锁
                NL->>API: patch 写入锁 (timestamp, ns, podname)
            else 锁已超时 (5min)
                NL->>API: 强制释放并重新获取
            else 锁属于同一 Pod
                Note right of NL: 视为已持有 (多厂商 Pod 复用)
            else 锁属于已删除 Pod
                NL->>API: 释放孤儿锁并重新获取
            else 锁被他人持有
                NL-->>B: ErrNodeLockContention
                B->>DM: 回滚已获取的所有锁
            end
        end
        Note over B: PodGroup 成员: 重试 28s<br/>非 PodGroup: 立即失败
    end

    B->>API: patch bind-phase=allocating 到 API
    B->>API: Pods().Bind() 执行 K8s 绑定

    alt 绑定成功
        B->>B: 记录绑定成功事件
    else 绑定失败
        B->>DM: releaseAllDevices() 释放所有锁
        B->>B: 记录绑定失败事件
    end

    B-->>KSC: ExtenderBindingResult{Result: true/false}
```

### 评分公式

**设备级评分**（`pkg/scheduler/policy/gpu_policy.go:200`）：
```
deviceScore = Weight × (slotWeight × (req+used)/count
                      + coreWeight × (reqCore+usedCore)/totalCore
                      + memWeight  × (reqMem+usedMem)/totalMem)
```

**节点级默认评分**（`pkg/scheduler/policy/node_policy.go:106`）：
```
nodeScore = Weight × (used/total + usedCore/totalCore + usedMem/totalMem)
```

**策略选择**：
- `binpack`：选分数最高（利用率最高）的节点 → 填满
- `spread`：选分数最低（利用率最低）的节点 → 分散

## 九、NUMA Refit 链路

当 kubelet 因 NUMA 拓扑选择了与 scheduler 不同的设备副本时，`/refit` 用于对齐：

```mermaid
sequenceDiagram
    autonumber
    participant KL as "kubelet"
    participant Route as "NumaRefit()"
    participant RF as "Scheduler.RefitNumaAllocation()"
    participant DP as "Device Plugin"

    KL->>Route: POST /refit (NumaRefitRequest)
    Route->>RF: WaitForCacheSync() 后调用

    RF->>RF: 读取 Pod 当前分配注解
    RF->>RF: 对齐 kubelet 选择的设备 ID<br/>与 scheduler 分配方案

    RF-->>KL: 对齐后的分配方案
```

**关键源码**：`pkg/scheduler/numa_refit_handler.go`

## 十、MIG 动态分配链路

MIG 模式下，scheduler 与 device plugin 协作创建/销毁 MIG 实例：

```mermaid
sequenceDiagram
    autonumber
    participant SE as "Scheduler"
    participant API as "kube-apiserver"
    participant DP as "Device Plugin"
    participant NVML as "NVML"
    participant MON as "vGPU Monitor"
    participant Lock as "MIG Apply Lock 文件"

    Note over SE: Filter 阶段: recordMigPlans() 规划 MIG 分配
    SE->>API: 写 hami.io/vgpu-mig-allocations 注解<br/>(profile, placement, GPU UUID)

    Note over DP: Allocate 阶段
    DP->>DP: 读取 MIG 分配注解
    DP->>Lock: CreateMigApplyLockDir() 创建锁文件
    Note over MON: WatchLockFile() 检测到锁文件<br/>暂停 Observe 反馈循环

    DP->>NVML: 创建 MIG 实例 (GI/CI)
    NVML-->>DP: MigUUID, GI ID, CI ID
    DP->>API: 更新注解, 补充运行时身份<br/>(MigUUID, GI/CI IDs)
    DP->>Lock: 删除锁文件
    Note over MON: 锁文件消失 → 恢复反馈循环

    DP->>DP: 返回 AllocateResponse
```

**关键源码**：
- `pkg/device/nvidia/mig_allocations.go` — MIG 分配注解编解码
- `pkg/device/nvidia/mig_topology.go` — MIG 拓扑冲突检测与联合规划
- `cmd/vGPUmonitor/main.go:90` — `WatchLockFile()` 协调
