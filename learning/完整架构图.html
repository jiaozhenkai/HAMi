① 端到端总览：谁调用谁

HAMi 横跨三层：控制面（Webhook + Scheduler Extender，cmd/scheduler）决定一个 Pod 用哪些设备；节点（Device Plugin + vGPU Monitor，DaemonSet）把决定落地；容器内（libvgpu.so）拦截 CUDA 调用做软隔离。编号箭头是一个 Pod 从提交到运行的调用顺序。注意容器与 Monitor 之间是双向共享内存——这是运行时隔离的关键（详见图⑦）。

② 部署形态：Helm Chart 如何落地

charts/hami/ 把 HAMi 落成两个工作负载：Scheduler 是 Deployment（多副本时只有 leader 提供服务），Device Plugin + vGPU Monitor 是 DaemonSet（每个加速器节点一份）。Webhook 不是独立进程，内嵌在 Scheduler 里。

③ Pod 生命周期时序：一个 Pod 经过的状态

把图①的箭头展开成时间轴。每一步对应一段代码：Webhook 改 spec、Extender 过滤评分并预占、Bind 取锁、Device Plugin 落环境变量、libvgpu 拦截、Monitor 限流。注意 /filter 同时做过滤+评分，只返回单个最优节点，不是候选列表。

④ 设备抽象层：一个接口，十六个后端

HAMi 的核心设计是设备后端插件化：所有硬件厂商实现同一个 device.Devices 接口（13 个方法），调度器只面向接口编程，不认识具体硬件。新增厂商 = 加一个 Init*Device 并在注册表里追加一行。

⑤ 调度器内部架构：一次 /filter 请求经过什么

Extender 是个 HTTP 服务（httprouter），6 条路由。请求进入后流经 路由层 → 调度核心 → 评分 → 缓存 → 策略 → 设备后端，/bind 路径额外取节点锁。注意 /filter 同时做过滤+评分，没有独立的 /score 路由。

⑥ 设备后端注册：启动时 DevicesMap 如何就绪

Extender 启动时调 config.InitDevicesWithConfig()，遍历一个 deviceInitializers 注册表，逐个调用各厂商的 Init*Device(config)，把返回的 Devices 实现塞进全局 DevicesMap[commonWord]。Ascend / Iluvatar 返回 []Devices（多芯片），需展开注册。

⑦ 运行时隔离机制：libvgpu ↔ Monitor 共享内存

这是 HAMi 最该画清楚的一张图：显存/算力隔离不是靠 cgroup，而是靠 libvgpu.so（LD_PRELOAD 进每个容器）与 vGPU Monitor 通过一个 mmap 的 .cache 文件双向通信。libvgpu 拦截每个 CUDA 内存分配与 kernel launch，按共享内存里的限值记账；Monitor 每 5 秒读使用量、回写限流信号。左边写什么，右边读什么；右边写什么，左边读什么——这就是全部机制。

⑧ 三种隔离模式：NVIDIA 后端的三条路

同一个 NVIDIA 后端，按配置走三条不同的隔离路径。这是“画差异”的一张图：三种模式在隔离强度、是否超卖、隔离手段上各不相同，决策点在 GPUCorePolicy / MigStrategy。

⑨ 关键注解参考 (hami.io/*)

HAMi 用 Pod / Node 注解在组件间传递设备分配状态——这些字符串就是组件之间的“协议”。来源：pkg/util/types.go 与 pkg/util/nodelock/nodelock.go。
